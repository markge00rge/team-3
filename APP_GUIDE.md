# Cairo Plant Supply Chain Optimizer

A desktop-oriented Streamlit application around the existing integrated V5
Pyomo/HiGHS optimizer. Only the Venus topology is supported. New Plant is a
clearly labelled future capability, not a second optimizer.

## Launch

From `OptimizationTrial` in PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app/main.py
```

Open http://localhost:8501. Dependencies are installed in the workspace virtual
environment. The application does not edit Word/Excel sources or historical
reports. Runs receive new UUID directories under `reports/app_runs/`.

## Demonstration

1. Open **Venus Case Study → Run Original Case**. This starts a new solver
   process, not a replay of the historical cost. No questionnaire is required.
2. Inspect stage-level proof and the resulting dashboards. Original run settings
   are frozen, even if a custom draft already exists.
3. Choose **Customize Parameters**, jump to **Distribution & Demand**, and
   change June H1 A/C demand from 105 to 115 MSU. The forecast becomes 3,105 MSU.
4. In **Review & Optimize**, name the scenario “Increased Summer Demand”,
   inspect differences, and click **Optimize Supply Chain**.
5. Open **Compare runs**. Select the two newly solved plans; inspect service
   before interpreting cost differences. Export scenario JSON and results.

Each of seven sections is prefilled. Values persist across page navigation.
Numeric controls have individual reset buttons; the sidebar resets the full
draft, and the forecast has a dedicated reset. Scenario JSON and demand CSV
imports are strictly validated and do not rewrite original documents.

## Truly editable fields and backend mapping

The complete allowlist is `app/scenarios.py: RULE_FIELDS` plus the enumerated
Venus keys generated by `original_scenario()`. Every key maps to CaseData and
rebuilds `src.model.build_model`; no duplicate case-input dataset lives in app/.

| Section | Editable | Destination / mathematical use |
| --- | --- | --- |
| Plant/products | Opening A/B/C finished stock; optimized qualification or selected qualification month | `initial_fp`, `qualification_allowed_months`; FP balances, daily candidate restriction |
| Manufacturing | L1/L2 daily MSU rates; optional upgrade permission per line | `lines.msu_per_day`, `upgrade_permissions`; daily capacities, monthly capacity expressions and rebuilt procurement bounds |
| Materials | A/C RM and PM BOM, opening material quantities; three scheduled receipt quantities | `bom`, `initial_materials`, `arrivals`; chronological material balances and consumption |
| Procurement | Integer sea-freight months, RM/PM lot sizes | `rules.sea_lead_months`, MOQ fields; receipt-month mapping, integer lot links and finite bounds |
| Material values/space | RM $/kg, PM $/EA, pallet factors, PM weight, disposal $/ton | Source rule fields; IDE, tracked warehouse and cash valuation. No independent material purchase expense |
| Workforce | Monthly wage, one-time hiring fee | Salary expressions include paid training and continued employment; hiring expense charged once |
| Warehouse/cash | On-site pallets, external rental rate, integer block size; A/B/C FP valuation, monthly holding fraction | Warehouse constraints, full-block rental objective, product-specific FP holding |
| Distribution | Dedicated fleet, truck MSU, spot surcharge, each hub's dedicated rate and shortage penalty | Truck/fleet constraints, destination costs, service penalties |
| Demand | All 72 month/hub/family forecast quantities | Source demand parameter and pooled A/C versus separate B demand balances, exact monthly priorities |

The UI displays percentages in percent units; JSON and the engine use fractions:
2% holding = `0.02`, 60% spot surcharge = `0.6`. Prices are inventory valuations,
not selling prices. RM quantities are kg, PM quantities are EA, production is MSU.

## Locked fields

Products A/B/C, family membership, A→C replacement, two lines, line eligibility,
three hub identities/priorities, horizon and 28-day month convention remain fixed.
Base/upgraded profiles, existing operators, ten-person additional crews, one paid
training month with zero extra output, three qualification days, routine
changeover rules, B smooth material replenishment, and the dates/types of the
three original receipts are read-only. External storage and unlimited spot-market
availability remain enabled; unsupported availability switches are not offered.

Choosing a qualification month restricts **the start month**, not a planning day.
The solver selects a valid three-day window under the original rules. Detailed
fixed-day scheduling and multi-month training are not advertised as editable.

## Configuration schema

`Scenario(schema_version=1, name, values)` is serialized as JSON. It includes all
supported defaults, not partial overrides. Extra/missing fields, unknown schema
versions, structural changes, nonfinite/negative numbers and fractional integer
parameters are rejected. Keys have forms:

```text
rule.fp_holding_fraction_month
rate.L1
upgrade.L2
qualification_month                 # "optimize" or a horizon month
bom.C.rm_kg_per_msu
bom.B.fp_usd_per_msu
initial_fp.A
stock.C.PM
receipt.0                           # existing receipt index; quantity only
hub.H1.truck_usd
demand.H1.AC.2027-06
```

The loader is the authority for the allowed identities and default values. Demand
CSV requires exactly `month,hub,family,msu` and the original 72 keys, with no
duplicates. A/C cannot be replaced by separate A and C forecasts.

## Execution, proof and data isolation

`Scenario → to_case() → build_model() → solve_lexicographic() → audit_solution()
→ extract_results() → independent financial/KPI calculations → dashboard`.

`app.jobs` launches a separate Python process, hidden on Windows. Streamlit polls
real events; it never invents solver completion percentages. Rerenders only poll,
and input edits cannot alter an already-running model. The worker creates an
immutable scenario snapshot and atomically publishes a completion marker after
output validation. No optimization is cached as a new execution.

The seven existing strict Scenario A stages are retained. There is no positive
cost tolerance or Scenario B. `--time-limit` / UI stage limits govern each full
solver stage; the existing optional procurement primal heuristic may take up to
20 extra seconds. Later stages run only after a proof. A time limit can publish
an audited incumbent with truthful incomplete proof; no result is fabricated
when the solver provides none. Errors and infeasibility remain visible.

Backend edits for this interface are limited to an optional observational stage
callback, safe financial recomputation for a feasible incumbent stopped before
the monetary stage, and source-derived pallet metadata so conservative peak
exports respect edited material footprints. No constraint, objective or business
assumption was changed. Training remains one month and is read-only.
Original adapter and independent CLI objectives are compared against the current
validated `reports/v5/solve_status.json`, not a hardcoded monetary constant.

## Dashboards and exports

Overview, Manufacturing, Materials, Warehouse & Cash, Distribution, Financials,
and C:D & Proof expose actual checked tables. Cost, cash, service and productivity
are separate. Inventory asset values are never added to expenses. Both cumulative
C:D interpretations remain diagnostics, with flags below one and undefined
zero-demand ratios left blank.

CSV downloads include production, material balances/orders, warehouse/inventory,
distribution, financial reconciliation and C:D; an Excel workbook includes all
tables. JSON exports include the scenario snapshot and actual proof metadata.
Comparisons use completed real runs, display service trade-offs, and never claim
like-for-like percentage savings when service differs. Saved V5 reference values
are explicitly labelled as historical and are not presented as a new solve.

## Validation commands

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m app.verify_scenarios --time-limit 180 --prefix acceptance
.\.venv\Scripts\python.exe -m src.solve --output-dir reports/app_runs/cli_original --time-limit 180
```

Acceptance directories are immutable; choose a new prefix for another verification
batch. The acceptance script runs Original Venus plus higher holding rate, higher
salary and increased June demand using the same adapter the UI worker uses.
`tests/test_app_execution.py` checks the actual artifacts and CLI equivalence;
it skips missing acceptance artifacts rather than substituting fake solves.
Lightweight mapping tests, Streamlit AppTest navigation/editor tests and the
existing backend suite run without re-solving four full-year cases every time.

## Remaining scope and next phase

See ASSUMPTIONS.md. Packaging age/expiry, physical B material footprint,
intramonth storage peaks, unknown labor ceiling/overtime and detailed daily
dispatch remain outside the accepted model. Complete physical real-world
feasibility is not claimed. Running a local Streamlit server is not deployment
with authentication, authorization or multi-user run management.

General-purpose plants require a generalized input schema, arbitrary eligibility,
family/replacement mappings, profile definitions, material/receipt identities,
transition rules and independent synthetic validation. Replace Venus-specific
source adaptation only after those mathematical generalizations are tested.
The Coming Next screen intentionally does not simulate this unsupported feature.

Implementation follows Streamlit's documented [widget state lifecycle](https://docs.streamlit.io/develop/concepts/architecture/widget-behavior)
and uses [AppTest](https://docs.streamlit.io/develop/api-reference/app-testing/st.testing.v1.apptest)
for page, editor, run-entry and dashboard tests. Durable scenario state is separate
from transient widget keys so page changes cannot erase business inputs.
